# 08 - 横切机制详解（守卫 / 拦截器 / 过滤器 / 白名单）

Nest 的请求生命周期横切层与 Hono 的完整对照。读完这章，Nest 版的任何横切代码你都知道该往哪搬。

## 8.1 三层机制对照总表

```
Nest 请求生命周期：
  请求 → 中间件 → 守卫(Guard) → 拦截器(前) → 管道(Pipe) → Controller
       → 拦截器(后) → 过滤器(ExceptionFilter) → 响应

Hono 请求生命周期：
  请求 → 中间件(前) → zValidator → handler → 中间件(后) → onError → 响应
```

| Nest | Hono | 在哪章 |
|---|---|---|
| `APP_GUARD` 全局守卫（SessionAuthGuard / AccessGuard） | `app.use('*', ...)` 全局中间件 / 路由级中间件 | 05、本章 8.2 |
| `@Public()` + Reflector 白名单 | 集中式路由白名单表（方法 + 路径模式） | 本章 8.3 |
| `APP_INTERCEPTOR`（日志、响应包装、ZodSerializer） | 中间件 `await next()` 之后的部分 | 本章 8.4 |
| `APP_PIPE`（ZodValidationPipe） | `@hono/zod-openapi` 内建校验 / `zValidator` | 05、06 |
| `APP_FILTER`（GlobalExceptionFilter） | `app.onError` + `app.notFound` | 03 |
| `Reflector` 元数据（@AccessPolicy） | 中间件参数（更显式） | 05 |

**关键认知**：Hono 没有 Nest 的五类扩展点，只有「中间件 + onError」两个钩子，但表达能力等价——中间件 `next()` 之前是守卫/拦截器前段，`next()` 之后是拦截器后段，onError 是过滤器。

## 8.2 守卫（Guard）

### 执行顺序的等价物

Nest 版在 `AppModule` 里注册顺序即执行顺序：

```ts
// Nest：APP_GUARD 注册顺序
{ provide: APP_GUARD, useClass: SessionAuthGuard }  // 先认证
{ provide: APP_GUARD, useClass: AccessGuard }       // 后鉴权
```

Hono 版用挂载顺序表达同样的语义：

```ts
// Hono：app.ts 中的挂载顺序
app.use('*', sessionAuth)                    // 全局认证（所有路由）
app.route('/auth', authRoutes)               // 公开路由在 sessionAuth 内被白名单放行
app.route('/companies', companiesRoutes)     // 业务路由各自挂 accessPolicy(...)
```

### 什么时候用全局中间件，什么时候用路由级

| 场景 | 做法 |
|---|---|
| 每个请求都要做（认证、requestId、日志） | `app.use('*', ...)` |
| 某组路由要做（鉴权策略） | 路由级：`app.get(path, accessPolicy(...), handler)` |
| 某个前缀都要做（如 `/admin` 要 adminOnly） | `app.use('/admin/*', accessPolicy({ scope: 'platform', adminOnly: true }))` |

## 8.3 白名单（@Public 的 Hono 实现）

Nest 版：`@Public()` 装饰器写元数据，守卫里 `reflector.getAllAndOverride(IS_PUBLIC_KEY)`。
Hono 没有装饰器扫描，推荐**集中式白名单表**——比散落的装饰器更好审计。

新建 `src/modules/auth/public-routes.ts`：

```ts
interface PublicRoute {
  /** 缺省匹配所有方法。 */
  readonly method?: string
  /** 精确路径，或以 * 结尾的前缀匹配。 */
  readonly path: string
}

/**
 * 公开路由白名单：认证与鉴权中间件共同读取。
 * 新增公开接口必须在这里登记——集中可审计，等同于 Nest 的 @Public()。
 */
export const PUBLIC_ROUTES: readonly PublicRoute[] = [
  { method: 'POST', path: '/auth/register' },
  { method: 'POST', path: '/auth/login' },
  { method: 'GET', path: '/health' },
  { path: '/api-docs/*' }, // Swagger UI 与其资源
] as const

/** 判断请求是否命中白名单。 */
export function isPublicRoute(method: string, path: string): boolean {
  return PUBLIC_ROUTES.some((route) => {
    if (route.method && route.method !== method) return false
    if (route.path.endsWith('*')) {
      return path.startsWith(route.path.slice(0, -1))
    }
    return path === route.path
  })
}
```

把 `session-auth.ts` 里的判断换成它：

```ts
import { isPublicRoute } from './public-routes'

export const sessionAuth = createMiddleware<AuthEnv>(async (c, next) => {
  if (c.req.method === 'OPTIONS') return next()
  if (isPublicRoute(c.req.method, c.req.path)) return next()
  // ...其余不变
})
```

`accessPolicy` 里同样加一行（防止公开路由误挂策略时被 403）：

```ts
if (c.req.method === 'OPTIONS' || isPublicRoute(c.req.method, c.req.path)) return next()
```

> **纪律**：白名单只有这一处。谁新增公开接口，谁改这张表，review 时一眼能看清系统有哪些"不设防"的入口——这比 Nest 的 `@Public()` 散落在各 Controller 里更严格。

## 8.4 拦截器（Interceptor）

Nest 拦截器的三件事——日志耗时、响应包装、响应序列化校验——在 Hono 里都是「`await next()` 之后继续执行」的中间件。

### ① 请求日志/耗时（对应 LoggingInterceptor）

新建 `src/common/http/timing.ts`：

```ts
import { createMiddleware } from 'hono/factory'

/** 记录每个请求的方法、路径、状态码与耗时。 */
export const timing = createMiddleware(async (c, next) => {
  const start = performance.now()
  await next()
  const ms = Math.round(performance.now() - start)
  console.log(
    JSON.stringify({
      event: 'http_request',
      requestId: c.get('requestId'),
      method: c.req.method,
      path: c.req.path,
      status: c.res.status,
      ms,
    }),
  )
})
```

挂在 `requestId()` 之后：`app.use('*', timing)`。

### ② 成功响应统一包装（对应 TransformInterceptor）

如果团队约定成功响应也包一层（如 `{ data, requestId }`）：

```ts
import { createMiddleware } from 'hono/factory'

/** 把 JSON 成功响应包装为 { data, requestId }；错误响应已由 onError 统一，不重复包。 */
export const wrapResponse = createMiddleware(async (c, next) => {
  await next()
  const res = c.res
  const contentType = res.headers.get('content-type') ?? ''
  if (res.status >= 400 || !contentType.includes('application/json')) return
  const body = await res.json()
  c.res = new Response(
    JSON.stringify({ data: body, requestId: c.get('requestId') }),
    { status: res.status, headers: res.headers },
  )
})
```

> **建议**：Nest 版没有包装成功响应（裸数据 + 错误走 ApiFailure），迁移期保持裸数据即可，这个中间件按需启用，别默认挂。

### ③ 响应 Zod 校验（对应 ZodSerializerInterceptor，防字段泄漏）

Nest 版用 `ZodSerializerInterceptor` 强制响应过 schema，多 select 一个字段都出不去。Hono 里用 zod-openapi 的 hook 在开发期兜底：

```ts
// app.ts 中创建 app 时
const app = new OpenAPIHono<AuthEnv>({
  defaultHook: (result, c) => {
    if (!result.success) throw result.error // 入参校验失败 → onError
  },
})
```

响应侧：zod-openapi 会对 `responses` 里声明了 schema 的 route 做**开发期校验告警**；要严格防泄漏，在 route 的 responses 里给每个 2xx 声明 zod schema（05、06 章已示范），handler 返回 `c.json(data)` 时多余字段不会被自动剥除——所以要像 Nest 版那样"序列化即契约"，给敏感接口加一层显式剥离：

```ts
// 对敏感接口：返回前显式过一遍 schema，剥掉未声明字段
return c.json(meSchema.shape.user.parse(user), 200)
```

> 实用折中：入参全靠 zod-openapi 自动校验（必做）；响应侧只对**含敏感字段的接口**（用户、成员）显式 `schema.parse` 剥离，其余信任 handler。

## 8.5 过滤器（Filter）

已在 03 章完成，这里只补两个容易漏的点：

1. **Hono 自带的 `HTTPException`**：第三方中间件（如将来加的限流）可能抛它。在 `onError` 的 `normalize()` 里加一个分支，映射到 `COMMON_ERRORS` 对应状态，避免它的 message 直接出网：

```ts
import { HTTPException } from 'hono/http-exception'

// normalize() 内，AppException 分支之后加：
if (exception instanceof HTTPException) {
  const status = normalizeStatus(exception.status)
  return {
    status,
    body: {
      code: 'COMMON.HTTP_' + status,
      message: status >= 500 ? COMMON_ERRORS.INTERNAL_SERVER_ERROR.publicMessage : '请求处理失败',
    },
    cause: status >= 500 ? exception : undefined,
    bearerChallenge: status === 401,
  }
}
```

2. **`notFound` 只是 404 这一种情况**：`method not allowed`（路径存在但方法不对）在 Hono 里也走 `notFound`，如需区分 405 可自行判断 `c.req.routePath`。

## 8.6 组装顺序全景（更新 app.ts 中间件段）

```ts
app.use('*', requestId())   // 1. 关联 ID
app.use('*', cors({...}))   // 2. CORS（预检直接终结，不进业务）
app.use('*', timing)        // 3. 日志耗时（拦截器后段在 next 之后）
app.use('*', sessionAuth)   // 4. 守卫①：认证（白名单在此放行）
// 5. 守卫②：鉴权 —— 各业务路由上的 accessPolicy(...)
// 6. 管道：zod-openapi 内建入参校验
// 7. 过滤器：app.onError / app.notFound 兜底一切异常
```

对照 Nest 版 `app.module.ts` 的注册表，每一项都有了归属。
